# Multisim 原生角落能力矩阵

## 2026-10-03 实机探测

本机通过 `tools/probe_multisim_native_api.py --blank` 探测了 Multisim 14.3 的
Automation API。结果同时保存在终端输出中；探测只读取类型库并创建未保存的空白电路，
不会修改用户工程。

| 能力 | 14.3 实测 | 当前含义 |
| --- | --- | --- |
| `EnumCircuitParameters` | 有 | 可以枚举电路参数入口，但不是写入授权 |
| `CircuitParameterValue` | 有 | 可以读取已知电路参数，但尚未发现可靠的全局温度 setter |
| `ReplaceComponent` | 有 | 可以替换器件，不能据此推断模型参数可原地写入 |
| 原生温度写入 | 无 | 温度角落保持 `unverified`，不能把普通 OP/AC/TRAN 当作温度验证 |
| 原生晶体管模型参数写入 | 无 | 不通过 COM 直接写模型；需要受控 XML 覆盖并经打开、保存、回读验收 |
| OP/AC 分析 | 有 | 已用于共射原生闭环 |

## 受控模型覆盖实验

对一个已完成验收的 2N3904 工程副本执行了以下闭环：

1. 解码 `.ms14`，同时修改 Q1 的模型正文和共享 `CiModel` 正文中的 `Bf=416.4` 为
   `Bf=200`；
2. 重新编码为新的 `.ms14`；
3. 用 Multisim 14.3 打开、保存到新的工程副本；
4. 再次解码保存后的工程，两个模型正文均仍为 `Bf=200`；
5. 运行原生 OP，基极、发射极和集电极读数发生相应变化。

这证明了模型参数覆盖存在可审计的实现路径，但只认证了该副本、该参数和 Multisim
14.3。实现正式角落扫描前，必须继续限制参数白名单、核对组件模型身份、保存前后哈希，
并为每个角落保留独立工程、CSV、报告和 manifest。

## 代码约束

- `native_capability_flags` 将参数读取、模型替换、温度写入和模型参数写入分开报告。
- `capability_profile` 对温度和晶体管参数写入保持保守的 `false`，不会因存在枚举 API
  而误报支持。
- 共射自然语言入口遇到温度请求时明确返回 `unverified` 原因，而不是生成普通原生结果
  后冒充完成温度验证。

下一步是把经过上述闭环认证的 2N3904 模型参数白名单接入角落扫描；温度角落仍需找到
Multisim 原生可回读的温度控制方式，或继续作为明确未认证能力保留。
